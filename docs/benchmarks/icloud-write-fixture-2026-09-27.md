# iCloud isolated write-fixture experiment — 2026-09-27

This is a protocol feasibility experiment, not a performance or reliability gate.
The normal Cirrove service and all existing mounts remain unchanged.

Question: Can Cirrove's own saved iCloud session create a new folder and a small
ordinary file in it, then locate the same provider IDs and read back exact bytes?
This does not establish update, replacement, trash, recovery, or concurrent
conflict behavior.

Arm: one invocation of the feature-gated native Rust write probe against the
isolated `iCloudGuiValidation` account. It generates a unique root folder whose
name starts `Cirrove Write Validation-`, writes only its own small text file,
and leaves the fixture visible for inspection. No existing user item is a target.
There is no comparative arm. The probe has no retry after an ambiguous mutation
response, because retry could create a duplicate. It prints stages, not tokens,
signed URLs, raw responses or file content.

Endpoint: a successful run requires the server to list the newly created folder,
return a file identity under it, and serve a byte-for-byte readback with matching
size. Record failed stage and duration without provider payloads. The prediction
is that folder creation will work with the observed web request shape; upload
registration is less certain, and a failed registration may leave an unattached
upload allocation. Do not infer an overwrite guarantee from either outcome.

Run environment: private `TMPDIR` and `SQLITE_TMPDIR` on btrfs under `/home`,
not tmpfs. No compilation or second measurement during the live invocation.
The run manifest in `.local-state/icloud-write-validation/manifest.json` records
the exact binary hash, command, temporary directory, PID and expected duration.
This artifact is completed with the observed outcome after the invocation.

## Observed first run

The pre-registered single run completed with exit code 0 in 44.2 seconds.
The probe created a unique validation folder under the existing iCloud Drive
root, found that same folder by ID, allocated and uploaded a small text file,
registered it under that folder, listed the new file by ID and size, and read
back the exact generated bytes. The fixture remains visible in iCloud Drive;
the probe made no request against a pre-existing file. This is one successful
account/session sample, not a reliability estimate or permission to enable
filesystem writes. It has no comparative arm or within-arm spread.

The next gate is safe replacement and stale-revision rejection against files
created by this probe, followed by crash/retry behavior and recovery. Until
those gates pass, iCloud stays a read-only Cirrove mount.
