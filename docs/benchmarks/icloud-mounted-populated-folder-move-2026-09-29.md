# Mounted iCloud populated-folder move — 2026-09-29

Registered before the live run. Only a new UUID-named Cirrove-owned folder in
the isolated `iCloudGuiValidation` account may be changed. The installed
daemon, normal iCloud mount, account settings and existing user files are
outside the run. The normal account remains read-only.

Question: does the provider-gated FUSE folder move retain a populated folder's
identity and child bytes when moving it between two owned parents, and can a
fresh process recover the same route after unmount?

Arms: create the isolated root with the existing mounted probe; create a
destination sibling and one small file below the source through the mount;
move the source into the destination through `rename(2)`; reopen the run in a
new process without issuing a mutation. Each stage must reach an applied
journal state before the next starts. An independent Apple session lists the
old and new parents, compares exact folder, destination and child IDs, and
reads all child bytes with SHA-256. Prediction: one exact folder move succeeds
and the fresh process sees unchanged IDs and bytes. If the move is uncertain,
the probe leaves its journal intact for inspection rather than retrying it.

Endpoints are the FUSE application's exit status, mutation/upload journal
states, independent listings and the complete child-file digest. This is one
small subtree and one run; it cannot establish concurrency, arbitrary subtree
depth or general iCloud reliability. No token, signed URL, cursor URL or raw
provider response is recorded.

Each exclusive stage records its command, binary SHA-256, PID, expected
duration and disk-backed `TMPDIR`/`SQLITE_TMPDIR` in a private manifest before
execution. No compilation or other measurement overlaps a stage.

## Observation

Run `a07ecbc6-7ad6-4d35-9314-24cc80b1c3c2` completed its initial create,
preparation and single mounted folder-move stages. All upload and mutation
rows expected by the probe reached `Uploaded` or `Applied`. The independent
iCloud listing found the source folder absent under the old parent and present
under the destination with its original ID. Its child kept its original ID
and the complete generated bytes matched the saved SHA-256. The FUSE
application also opened those bytes immediately after `rename(2)`.

The first fresh-process read stopped before mounting with `non-fixture rename
in isolated journal`. The fixture's ownership-recovery allowlist understood
same-parent folder rename but not the newly confirmed cross-parent move. This
was a local validator omission; no second cloud move was sent. The correction
requires the destination's own applied create receipt and the exact owned
source ID, parent and name. A new targeted test executed and passed, then a
fresh process ran the read-only remount successfully. It verified the same
folder, destination and child IDs and the complete child bytes against the
pre-move record. The run directory and all journals are retained.
