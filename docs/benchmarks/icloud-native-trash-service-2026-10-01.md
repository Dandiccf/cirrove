## Kernel held-reader preregistration

Question: after confirmed native removal and ordered absence publication, does
the package disappear while an already-open generated artifact keeps its exact
verified bytes without additional remote content reads?

One synthetic FUSE arm:
`cargo test -p cirrove-service --test writable_session real_native_trash_publication_preserves_held_generated_archive_reader -- --ignored --exact --nocapture`.

The fixture models verified generated bytes, then injects one exact confirmed
receipt into the journal. Store-only waiting requires the real publication worker;
it cannot shortcut refresh through a test lookup. The root view must omit the
package and a new open must fail ENOENT, while the held FD reads identical bytes
and SHA with provider content reads disabled. Existing installed mounts untouched.
Prediction: immutable held-reader version remains readable after namespace removal.
No Apple ZIP parser, live Trash, public admission or performance guarantee is
claimed by this arm. Private disk-backed temporary paths and exclusive runner
manifest identify the command before it starts; no other build/run is concurrent.

The baseline arm passed (one test, 1.08 seconds). Negative-control prediction:
removing only the native Trash publication worker spawn must fail the Store-only
absence wait; the receipt alone cannot remove the visible package. Source is
restored in a finally block before subsequent integration.

Correction: the worker-removal negative control ALSO passed (5.08 seconds).
Therefore the original Store-only wait does not isolate the dedicated publication
worker; another background refresh can publish absence. This arm currently proves
held-reader lifetime through namespace removal, not which worker caused removal.
The negative-control source was restored. Dedicated publication behavior retains
its separate journal/publication unit evidence; stronger kernel isolation is under review.

## Corrected kernel acceptance and retained lookup

publication acknowledgement (`done=1`), independently of visible namespace

completion together with held-reader lifetime, not exclusive causation of the
namespace refresh and not a performance result.

## Bounded public recovery acceptance

The escaped-metadata regression first failed with an oversized page
(`native-trash-list-budget-red`). The fixed implementation budgets 512 KiB for
serialized selections, preserves the overflowing row for the next page and
retains bounded legacy-history scanning. Eighty heavily escaped valid IDs and
revisions round-trip in order without missing/duplicate operations in both modes.

`native-trash-list-restart-integrated` passed the focused native Trash suite,
including actual socket reply loss, dropping the original Engine/Manager/journal,
and reconstructing a read-only Manager with empty jobs and no writer. The public
list discovers the same Pending UUID, selected identity and revision. Every
provider API in the restarted fixture panics if called; repeated listing does
not recreate a job or retry a mutation, and a foreign account is refused.
These are synthetic local restart tests, not installed/live-provider acceptance.

Full-check integration found legacy tests whose expected current/future journal
versions still used 15/16 after the intentional schema16 fence. The package
publication fixture now explicitly constructs a schema15 migration input;
current-version assertions use16 and unknown-future assertions use17. Nine
focused affected integration binaries passed (`native-trash-schema-regression`).
The read-only local-export future-version fixture was likewise updated to17.
No production compatibility guard was relaxed. Two Clippy style findings were
also corrected before rerunning the full script.
